O seu app Rails envia e-mail com a Resend, e você quer testar o 1billion. Não precisa de um grande dia de troca. Os dois serviços rodam lado a lado, e você move um mailer por vez, começando pelo que mais importa: o código de login.

Este post mostra cada passo. Os mailers e as views do seu app não mudam.

## De onde você parte

Com a Resend, um app Rails tem o gem `resend`, uma chave num initializer e uma linha de config:

```ruby
# Gemfile
gem "resend"

# config/initializers/mailer.rb
Resend.api_key = ENV["RESEND_API_KEY"]

# config/environments/production.rb
config.action_mailer.delivery_method = :resend
```

## 1. Adicione o gem do 1billion

```bash
bundle add 1billion
```

Mantenha o gem `resend` por enquanto: os dois delivery methods convivem. Depois dê a chave ao app, como você fez com o `RESEND_API_KEY`:

```bash
ONEBILLION_API_KEY=ob_...
```

O gem lê o `ONEBILLION_API_KEY` sozinho, então não há initializer para escrever. Se você guarda as chaves nas credentials do Rails, uma linha resolve:

```ruby
# config/initializers/onebillion.rb
OneBillion.api_key =
  Rails.application.credentials.dig(:onebillion, :api_key)
```

Crie a chave de API no [console](https://app.1billion.clowk.in), na página do seu app. Guardamos só o hash de cada chave: se perder uma, crie outra e revogue a antiga.

## 2. Verifique o domínio, com a Resend ainda ligada

Adicione o seu domínio ao app no console. São dois registros obrigatórios: um TXT em `1billion._domainkey.<domínio>` com a chave DKIM, e um CNAME para o return path, que leva o SPF e o MX. O return path é `1billion.<domínio>` por padrão, e o console mostra o nome e o valor exatos para copiar. Uma política DMARC é recomendada; se o seu domínio já tem uma, mantenha.

Na Cloudflare, deixe os registros como DNS only (a nuvem cinza).

![A página de um domínio no console do 1billion: os registros de DKIM, return path e DMARC, cada um verificado, e um cURL para enviar o primeiro e-mail.](/blog/rails-from-resend/domain-dns.png)

Esses nomes não são os que a Resend usa, então os registros dos dois serviços ficam juntos no seu DNS. A Resend continua enviando enquanto o console checa os registros novos. Veja [Domains and DNS](/docs/guides/domains).

## 3. Mova um mailer

Um mailer pode escolher o seu próprio delivery method. Comece pelo e-mail que a pessoa espera:

```ruby
class LoginMailer < ApplicationMailer
  self.delivery_method = :onebillion

  def code(user, code)
    @code = code

    mail(to: user.email, subject: "Seu código")
  end
end
```

Todos os outros mailers continuam pela Resend. Acompanhe o e-mail de login no console por um dia: cada destinatário tem a sua mensagem, com o status e a última resposta do servidor remoto.

## 4. Impeça que um job repetido envie duas vezes

O gem envia a mensagem MIME pronta, e usa o `Message-ID` dela como `Idempotency-Key`: a mesma chave em 30 dias devolve a primeira resposta e não envia nada de novo.

O `deliver_later` gera o e-mail de novo dentro do job. Se o job roda duas vezes, a segunda tem um `Message-ID` novo, então é um e-mail novo. Para o e-mail que nunca pode sair duas vezes, defina um `Message-ID` que dê nome ao e-mail:

```ruby
mail(
  to: user.email,
  subject: "Seu código",
  message_id: "<login-#{user.id}-#{code}@acme.com>"
)
```

## 5. Decida o que uma entrega que falhou faz

O gem já tenta de novo num `503` ou num erro de rede, 3 vezes, com a mesma chave. Os outros erros chegam ao job de entrega, e você escolhe o que cada um faz:

```ruby
# config/initializers/onebillion.rb
Rails.application.config.after_initialize do
  job = ActionMailer::MailDeliveryJob

  # Fora do ar mais tempo do que o gem espera: tente depois.
  job.retry_on OneBillion::Error,
    wait: :polynomially_longer, attempts: 10

  # Sem créditos hoje: eles voltam à meia-noite.
  job.retry_on OneBillion::NoCredits, wait: 1.hour, attempts: 24

  # Mensagem ou destinatário ruim: repetir dá a mesma resposta.
  job.discard_on OneBillion::Refused
end
```

`NoCredits` e `Refused` são tipos de `OneBillion::Error`. O Active Job olha primeiro o handler declarado por último, então declare o geral primeiro, como aqui.

## 6. Mova as chamadas à API

Código que chama a API da Resend direto muda um nome só. Os campos são os mesmos:

```ruby
# Antes
Resend::Emails.send({
  from: "Acme <hi@acme.com>",
  to: ["jane@example.com"],
  subject: "Seu recibo",
  html: "<p>Obrigado pelo pedido.</p>"
})

# Depois
OneBillion::Emails.send({
  from: "Acme <hi@acme.com>",
  to: ["jane@example.com"],
  subject: "Seu recibo",
  html: "<p>Obrigado pelo pedido.</p>"
})
```

Ele devolve o `id` do e-mail, como a Resend. Um campo que o 1billion ainda não tem levanta um erro com o nome dele, então nada some sem você saber. Para uma retentativa segura, passe uma chave: `OneBillion::Emails.send(params, idempotency_key: "receipt-#{order.id}")`.

## 7. Mova os webhooks

A Resend assina os webhooks com headers do Svix. O 1billion assina com `1B-Timestamp` e `1B-Signature`, e o gem checa os dois numa chamada: a assinatura, e se o evento tem menos de 5 minutos.

```ruby
class OneBillionWebhooksController < ActionController::API
  def create
    event = OneBillion::Signature.verify(
      payload: request.raw_post,
      headers: request.headers
    )

    # event["type"]: delivered, bounced ou unsubscribed.
    # Use event["id"] para ignorar um evento repetido.
    head :no_content
  rescue OneBillion::Signature::Invalid
    head :unauthorized
  end
end
```

O segredo vem do `ONEBILLION_WEBHOOK_SECRET`; copie da página do app. Deixe os dois endpoints rodando enquanto os dois serviços enviam. Veja [Webhooks](/docs/guides/webhooks).

## 8. Troque o resto, e tire a Resend

Quando o e-mail de login estiver bem, mude o padrão e tire o `self.delivery_method` dos mailers:

```ruby
# config/environments/production.rb
config.action_mailer.delivery_method = :onebillion
```

Depois tire o gem `resend`, o initializer e a chave dele, e remova os registros DNS dele quando tiver certeza.
